# 数据库备份与隔离恢复 Runbook（草案）

## 状态

本 Runbook 只定义安全流程。独立备份目标、目标账户与区域、备份密钥托管、精确备份范围、RPO 和 RTO 尚未由用户确认，因此当前代码不会连接真实目标，也不会创建或清理真实备份。

## 不可变边界

- 备份目标必须独立于主 Supabase 项目。
- 备份密钥不得复用 `PROVIDER_MASTER_KEY`，不得进入命令参数、日志、清单或数据库正文。
- 逻辑转储先写入权限为 `0600` 的临时文件，在离开进程前使用独立 AES-256-GCM 密钥加密；明文加密后立即删除。
- 上传必须禁用覆盖，并再次核对目标版本、密文字节数和 SHA-256。
- 上传成功只表示“密文已保存”，不表示“可恢复”。只有隔离恢复、迁移版本核对和业务一致性检查全部通过，才能记录为 `verified`。
- 备份清理默认关闭。没有用户再次明确授权，不删除任何备份。

## 待确认的备份范围

逻辑备份使用明确表白名单，不备份整个 Supabase 平台。

| 范围 | 当前草案 |
|---|---|
| 包含 | Paper Grading 业务表、迁移版本和必要序列 |
| 排除 | `auth`、`storage` Schema、Storage 文件、Redis、部署配置和所有密钥 |
| 外部依赖 | 相同 UUID 的 Auth 用户、主项目 Storage 对象、供应商主密钥 |

数据库备份只包含 Storage 元数据时，不能恢复实际 Storage 文件。正式接入前必须决定是否另建独立的 Storage 对象备份流程。

## 创建流程

1. 备份 Worker 用独立最小只读数据库角色创建一条带租约的 `backup_runs`。
2. 使用受控的 `PGPASSFILE` 和表白名单执行逻辑转储；密码不得出现在进程参数或日志。
3. 记录转储工具版本、迁移版本、明文大小和 SHA-256。
4. 从用户确认的密钥托管位置取得独立备份密钥，用备份 UUID、envelope 版本和 key ID 作为认证上下文进行流式加密。
5. 删除明文，只把密文不可覆盖地上传到独立目标。
6. 从目标读取对象元数据，核对版本、大小和密文 SHA-256。
7. 保存不含凭据的 manifest；此时状态只能是 `completed`，不能是 `verified`。
8. 任一步失败都保存稳定错误码，并清理本机临时文件；不把第三方错误正文写入数据库或日志。

## 隔离恢复流程

1. 创建与生产隔离、网络和权限受控的临时 PostgreSQL 环境；禁止指向生产数据库。
2. 记录恢复环境指纹，并确认可安全销毁。
3. 准备 manifest 所要求的 Auth 用户 UUID；如果备份包含加密的供应商配置，还必须准备原 `PROVIDER_MASTER_KEY`，否则不得声称该范围已恢复。
4. 从独立目标按 manifest 的对象键和版本下载密文，核对密文字节数和 SHA-256。
5. 从托管位置取得 manifest 指定 key ID 的备份密钥，解密后核对明文字节数和 SHA-256。
6. 把隔离库迁移到 manifest 记录的迁移版本，再恢复白名单数据。
7. 至少核对：
   - 所有白名单表行数和外键；
   - 作业、Rubric、批次、attempt、教师确认和导出快照的引用完整性；
   - 金额、Token、分数和反馈字段可读；
   - 审计记录仍为只追加；
   - Storage 对象明确标记为“未由数据库逻辑备份覆盖”，不能误报为已恢复。
8. 只有全部检查通过才写入 `backup_restore_runs.status = verified`；失败时写稳定错误码，不改动最近一次成功证明。
9. 销毁隔离环境和本地解密文件；不得触碰生产环境。

## 回滚

- 创建失败：保留失败状态，重用同一备份 UUID 时只允许目标返回完全相同的对象版本和哈希。
- 上传后数据库断连：下一次先核对目标已有对象，禁止覆盖或创建同名不同内容。
- 恢复失败：销毁隔离环境，从最近一次已验证备份重新开始；不得把部分恢复数据合并到生产库。
- 清理失败：保持旧备份，不通过扩大删除范围补偿。
